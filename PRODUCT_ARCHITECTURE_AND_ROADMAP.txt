ImpactR
Product Architecture, Current Implementation, and Future Roadmap
=================================================================

Document status: Prototype architecture and production roadmap
Problem statement: SIH26152 - Social Media Analytics
Theme: Blockchain and Cybersecurity
Primary product goal: Evidence-first social intelligence for authorized sources


1. PRODUCT SUMMARY
------------------

ImpactR is a social intelligence and narrative analysis platform. It collects
authorized social-media events, stores the original source payload, normalizes
the event into a common schema, analyzes the content, and presents findings in
an analyst dashboard.

The most important product principle is evidence separation:

  OBSERVED FACT
    Something directly present in a source event, such as text, timestamp,
    platform, public engagement counts, or a relationship between records.

  MODEL OUTPUT
    A result generated by a machine-learning model, such as sentiment,
    emotion, embedding, topic similarity, or confidence.

  ANOMALY SIGNAL
    A pattern that deserves review, such as synchronized activity or repeated
    content. It is not automatically proof of malicious intent or automation.

  SUPPORTING EVIDENCE
    The source events and measurable features that support a finding.

ImpactR must never claim that an account is a bot, a post is false, or a
narrative is malicious without evidence and an analyst review process.

3. CURRENTLY IMPLEMENTED
------------------------

3.1 Backend entrypoints

The project currently has two backend modes:

  Demo API
    File: backend/app/main.py
    Purpose: Offline prototype and synthetic Project Orion demonstration.
    Data: In-memory synthetic events.
    Endpoints: Dashboard, demo investigation, demo simulation, WebSocket.

  Production ingestion API
    File: backend/app/real_main.py
    Purpose: Authorized X and Telegram ingestion.
    Data: SQLite WAL persistence through ProductionPipeline.
    Endpoints: health, sources, events, poll, investigation, WebSocket.

The frontend is connected to the production event endpoint for the live source
view. The synthetic investigation and production investigation are separate
concepts and should be kept clearly labeled in future UI work.

3.2 X adapter

ImpactR uses the official X API v2 recent-search endpoint. It does not scrape
X HTML. The current request includes tweet fields for:

  - created_at
  - public_metrics
  - author_id
  - language
  - entities

The required environment variable is:

  X_BEARER_TOKEN

The token can be valid while the endpoint is unavailable for the project plan.
The current project has observed HTTP 402 Payment Required from X, which means
the credential is recognized but the requested API access or credits are not
available.

3.3 Telegram adapter

ImpactR uses the official Telegram Bot API getUpdates method. The bot must be
able to access the target chat or channel. The current environment variable is:

  TELEGRAM_BOT_TOKEN

The current collector supports message, channel_post, and edited_channel_post
updates. It does not read arbitrary Telegram history. For historical public
channel analysis, an explicitly authorized MTProto client is required.

3.4 Event normalization

The normalized event model contains:

  id
  platform
  platform_post_id
  author_id
  author_name
  text
  timestamp
  language
  reply_to
  parent_post_id
  like_count
  share_count
  reply_count
  view_count
  url
  hashtags
  mentions
  metadata

Raw source data is retained in the production pipeline. Author identifiers are
hashed before persistence in the production event store.

3.5 Persistent analysis pipeline

File: backend/app/services/production_pipeline.py

The pipeline currently creates two SQLite tables:

  source_events
    Stores normalized events, source identity, hashes, timestamps, and the raw
    source payload.

  analyses
    Stores sentiment, confidence, emotion, keywords, embedding, model version,
    and analysis timestamp.

The pipeline deduplicates by event ID or platform plus platform post ID.

3.6 AI pipeline

The production environment now includes:

  - PyTorch CPU
  - Hugging Face Transformers
  - DistilBERT sentiment classification
  - sentence-transformers
  - all-MiniLM-L6-v2 style embedding generation
  - scikit-learn
  - NetworkX

The current AI behavior is:

  Sentiment
    Transformer-powered when the model is available.

  Embeddings
    Sentence-transformer-powered when the model is available.

  Emotion
    Currently a transparent rule-based classifier. This should be replaced by
    a multilingual emotion model or a fine-tuned internal classifier.

  Keywords
    Lightweight keyword extraction from normalized tokens.

The model version is persisted with each analysis so results can be reproduced
and compared after model upgrades.

3.7 Frontend

The frontend is a Next.js application with React, TypeScript, Tailwind-style
layout conventions, Recharts, and Framer Motion.

Current product views include:

  - ImpactR dashboard
  - real event feed
  - source status indicators
  - topic and sentiment display areas
  - evidence stream
  - investigation route
  - propagation visualization
  - coordination signal panel

The UI was intentionally restyled into a restrained analyst workspace with a
light neutral palette, small status indicators, clear table-like rows, and no
neon or futuristic visual language.

3.8 Deployment

Docker Compose defines:

  - frontend
  - backend
  - PostgreSQL
  - Redis

The environment currently supports direct local execution more reliably than
Docker because the available machine does not have the Docker Compose plugin.


4. CURRENT DATA FLOW
--------------------

1. The API starts and reads environment variables.
2. The source poller checks whether X and Telegram credentials exist.
3. The authorized adapter makes an HTTPS API request.
4. The response is converted to the normalized event schema.
5. The pipeline checks for an existing event ID or platform post ID.
6. New events are stored with the raw source payload.
7. Transformer sentiment and sentence embeddings are generated.
8. Emotion and keyword results are generated.
9. Analysis results are persisted with the model version.
10. The event can be returned through REST and WebSocket endpoints.
11. The frontend renders source events and evidence.

When X returns an error, Telegram ingestion continues independently. This is
important because one provider must not stop all collection.


5. CURRENT LIMITATIONS
----------------------

The following limitations are known and should be treated as roadmap items:

  - The production pipeline currently uses SQLite WAL rather than PostgreSQL.
  - The production event API and demo dashboard APIs are not yet unified.
  - The production investigation endpoint is currently a basic evidence view.
  - Emotion classification is rule-based rather than transformer-based.
  - Narrative clustering and trend calculations are not yet fully connected to
    live production events.
  - The X recent-search endpoint requires the correct paid access or credits.
  - Telegram Bot API cannot retrieve arbitrary historical channel data.
  - No analyst authentication or role-based access control is active yet.
  - No formal retention or deletion scheduler is active yet.
  - No production alerting, metrics, tracing, or incident response integration
    is active yet.
  - The Docker Compose stack has not replaced direct local development as the
    default workflow.


6. PRODUCTION HARDENING ROADMAP
-------------------------------

Priority 0 - Make the current path reliable

  1. Unify the frontend against the production API contract.
  2. Add typed Pydantic schemas for all production responses.
  3. Add structured error responses instead of raw provider exceptions.
  4. Add provider-specific health states:
       NOT_CONFIGURED
       AUTHENTICATED
       ACCESS_DENIED
       RATE_LIMITED
       BILLING_REQUIRED
       DEGRADED
       HEALTHY
  5. Add persistent source cursors and Telegram update offsets.
  6. Add retries with exponential backoff and a dead-letter queue.
  7. Add automated tests with mocked X and Telegram responses.

Priority 1 - Persistent production data layer

  1. Move normalized events to PostgreSQL.
  2. Use SQLAlchemy models and Alembic migrations.
  3. Add PostgreSQL indexes for timestamp, platform, source ID, topic, and
     investigation queries.
  4. Enable pgvector for embeddings.
  5. Store model inputs and outputs with model hash and preprocessing version.
  6. Add retention policies for raw payloads and hashed identifiers.
  7. Add backup, restore, and migration procedures.

Priority 2 - Real AI intelligence layer

  1. Replace rule emotion detection with a multilingual emotion model.
  2. Add language detection using fastText or a transformer model.
  3. Add named entity recognition using spaCy or a multilingual Hugging Face
     model.
  4. Add sarcasm and uncertainty indicators as separate model outputs.
  5. Add multilingual embedding support for Indian languages.
  6. Use pgvector nearest-neighbor search for semantic narrative matching.
  7. Cluster embeddings with HDBSCAN or an equivalent density-based method.
  8. Generate narrative names from extracted keywords and representative posts.
  9. Calibrate model confidence on a reviewed validation set.
  10. Add analyst feedback loops for correction and retraining.

Priority 3 - Trend and narrative intelligence

  1. Create fixed time buckets for topic counts.
  2. Calculate velocity, acceleration, engagement velocity, novelty, and
     cross-platform presence from persisted data.
  3. Store every trend snapshot so historical scores are reproducible.
  4. Implement the transparent trend formula:

       trend_score =
         normalized_velocity * 0.35 +
         normalized_acceleration * 0.25 +
         normalized_engagement * 0.20 +
         cross_platform_factor * 0.20

  5. Add rising, emerging, stable, and declining classifications.
  6. Add narrative lifecycle states:
       first_seen
       growing
       cross_platform
       peak
       declining
       dormant
  7. Link every narrative statement to representative source events.

Priority 4 - Graph and propagation analysis

  1. Build a NetworkX graph from users, posts, topics, channels, and URLs.
  2. Add typed edges:
       POSTED
       REPLIED_TO
       MENTIONED
       RESHARED
       FORWARDED
       ABOUT
       SIMILAR_TO
  3. Calculate degree centrality, betweenness centrality, PageRank, and
     community structure.
  4. Use neutral terms such as “high network centrality”.
  5. Add temporal graph snapshots.
  6. Add first-seen and first-cross-platform timestamps.
  7. Add evidence inspection for every graph edge.
  8. Move to Neo4j only when graph scale and query complexity justify it.

Priority 5 - Coordination and anomaly analysis

  1. Calculate posting frequency and inter-post interval distributions.
  2. Detect repeated text and high semantic similarity.
  3. Detect shared URLs, shared hashtags, and synchronized bursts.
  4. Compare network neighborhoods and interaction patterns.
  5. Build a reviewable anomaly score, not a bot verdict.
  6. Store feature values used by each signal.
  7. Show accounts, time window, similarity, URLs, and source posts.
  8. Add false-positive review workflows.
  9. Evaluate the model on synthetic and analyst-reviewed datasets.

Priority 6 - Security and governance

  1. Add OAuth2 or OIDC authentication.
  2. Add role-based access control:
       viewer
       analyst
       investigator
       administrator
  3. Add tenant or agency isolation.
  4. Encrypt secrets through a secret manager.
  5. Encrypt sensitive data at rest and in transit.
  6. Add audit logs for searches, exports, evidence views, and investigations.
  7. Add rate limiting and request size limits.
  8. Add network egress policies for source connectors.
  9. Add privacy review and data protection impact assessment.
  10. Add deletion workflows and retention enforcement.

Priority 7 - Operations and deployment

  1. Move ingestion to Celery or an asyncio worker service.
  2. Use Redis Streams or Kafka for durable event transport.
  3. Add Prometheus metrics and Grafana dashboards.
  4. Add OpenTelemetry traces across adapter, pipeline, and API calls.
  5. Add Sentry or equivalent exception tracking.
  6. Add health checks for database, Redis, provider APIs, and model loading.
  7. Add CI for linting, tests, migrations, security scanning, and builds.
  8. Add blue-green or rolling deployment.
  9. Add separate demo, staging, and production environments.
  10. Add disaster recovery runbooks.


7. FUTURE PRODUCT FEATURES
---------------------------

7.1 Investigation workspace

  - Saved investigations
  - Analyst notes
  - Evidence pinning
  - Exportable PDF and JSON reports
  - Timeline annotations
  - Review and approval states
  - Collaboration and handoff between analysts

7.2 Advanced source support

  - Authorized Telegram MTProto history ingestion
  - Reddit official API
  - YouTube Data API
  - RSS and government bulletin sources
  - Webhook-based source ingestion
  - Source-specific rate limit dashboards

7.3 Indian language intelligence

  - Hindi, Tamil, Telugu, Bengali, Marathi, Kannada, Malayalam, Gujarati,
    Punjabi, and other language pipelines
  - Transliteration normalization
  - Code-mixed language detection
  - Regional slang and phrase dictionaries
  - Language-specific sentiment and emotion calibration

7.4 Explainability

  - Representative posts for every narrative cluster
  - Feature contribution summaries
  - Confidence calibration views
  - Model version comparison
  - Data quality warnings
  - Explicit distinction between evidence and inference

7.5 Alerts

  - Topic velocity threshold alerts
  - Cross-platform spread alerts
  - Shared URL burst alerts
  - Sudden sentiment shift alerts
  - Analyst-configured watchlists
  - Email, webhook, and secure notification integrations

7.6 Blockchain and integrity layer

  Blockchain should be used for evidence integrity, not as a decorative
  feature. Potential uses include:

  - Hashing source payloads into an append-only evidence ledger
  - Merkle roots for batches of collected events
  - Timestamping investigation snapshots
  - Signing exported reports
  - Verifying that an evidence record was not modified after collection
  - Permissioned ledger integration for multi-agency workflows

  Raw sensitive content should not be placed directly on a public blockchain.
  Store content in controlled storage and put only hashes, timestamps, and
  provenance references into the integrity layer.

-------------------------------

  Frontend
    Next.js, TypeScript, React, Recharts, React Flow or Cytoscape.js.

  API
    FastAPI, Pydantic, SQLAlchemy, WebSockets.

  Workers
    Celery or asyncio worker services with explicit retry and dead-letter

  AI
    Hugging Face Transformers, sentence-transformers, PyTorch CPU or GPU
    inference service, scikit-learn for clustering and anomaly models.

  Graph
    NetworkX initially, Neo4j when graph persistence and traversal scale
    require it.

  Operations
    Docker, Kubernetes when needed, Prometheus, Grafana, OpenTelemetry,
    centralized structured logs, and secret management.


9. DEFINITION OF PRODUCTION READY
---------------------------------

ImpactR should not be called production ready until all of the following are
true:

  - Authorized source adapters have documented access requirements.
  - Provider failures do not stop other providers.
  - Events are durable, deduplicated, and replayable.
  - AI outputs include model version and confidence.
  - Every finding links to underlying evidence.
  - PostgreSQL persistence and backups are operational.
  - Authentication, RBAC, audit logs, and retention are enabled.
  - Model performance has been evaluated on representative data.
  - Monitoring and alerting are active.
  - The deployment process is repeatable and tested.
  - Analysts can distinguish observed facts from inferences.
  - Privacy and legal review has approved the collection scope.


10. FINAL PRODUCT DIRECTION
---------------------------

ImpactR should become a calm, evidence-first investigation system rather than
a dashboard that produces dramatic labels. The strongest version of the
product will make it easy for an analyst to answer:

  What was observed?
  When did it happen?
  Where did it first appear?
  How did it spread?
  What model output was generated?
  How certain is that output?
  What evidence supports it?
  What alternative explanations remain?
  What action is justified?

That standard should guide all future source integrations, AI features, graph
visualizations, alerts, and security controls.
